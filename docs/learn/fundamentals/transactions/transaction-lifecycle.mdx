title: Transaction Lifecycle

### 1. Create

A user creates a transaction by setting its source account, sequence number, operations, fee, and any optional memo or preconditions.

#### 1b. Simulate

Smart contract transactions are run in a simulated environment to check for errors and assemble the data they need to execute. Learn more about [simulation](../contract-development/contract-interactions/transaction-simulation.mdx).

### 2. Sign

The completed transaction is wrapped in a transaction envelope that carries its signatures. A simple transaction often needs only its source account’s signature; a multisignature setup may require several. Learn more about [signatures and multisig](./signatures-multisig.mdx).

### 3. Submit

The signed transaction is submitted to the Stellar network, typically through [Stellar RPC](../../../data/apis/rpc/README.mdx). Stellar Core immediately rejects an invalid transaction without consuming its source account’s sequence number or fee. A transaction can also be submitted directly to a Stellar Core node.

### 4. Propagate

After validating the transaction, Stellar Core floods it to connected peers, which relay it across the network.

### 5. Build a candidate set

When it is time to close a ledger, each validator collects the valid transactions it knows about into a candidate set encoded as [transaction-set XDR](https://github.com/stellar/stellar-xdr/blob/main/Stellar-ledger.x#L226-L245). Transactions arriving after construction begins wait for the next ledger. If demand exceeds a ledger limit, [surge pricing](../fees-resource-limits-metering.mdx#surge-pricing) prioritizes transactions for inclusion.

### 6. Nominate

Each validator nominates its candidate set through [SCP nomination](../stellar-consensus-protocol.mdx#nomination-protocol).

### 7. Reach consensus

[SCP](../stellar-consensus-protocol.mdx) resolves differences among candidate sets and selects the transaction set, close time, and protocol upgrades for the ledger.

Transactions omitted from the final set remain in each validator’s local queue for best-effort inclusion in a later ledger. Stellar Core [ages queued transactions by source account](https://github.com/stellar/stellar-core/blob/master/src/herder/TransactionQueue.h#L50-L58). After its [four-ledger timeout](https://github.com/stellar/stellar-core/blob/master/src/herder/HerderImpl.cpp#L62-L63), it evicts and bans all queued transactions from that source account for 10 ledgers.

### 8. Determine apply order

After SCP finalizes the transaction set, every validator derives the same apply order from the set’s hash. Stellar Core’s [`ApplyTxSorter`](https://github.com/stellar/stellar-core/blob/master/src/herder/TxSetFrame.cpp#L179-L195) orders transactions using their full hashes and the final transaction-set hash. This deterministic mixing makes relative order difficult to predict before the set is known. Transactions from the same source account still follow sequence-number order.

### 9. Collect fees

Before executing transactions, Stellar Core [processes fees and sequence numbers](https://github.com/stellar/stellar-core/blob/master/src/ledger/LedgerManagerImpl.cpp#L2425-L2544) for the entire set in a single pass.

### 10. Apply transactions

Stellar Core applies each transaction in the computed order. It consumes the source account’s sequence number, rechecks validity, and runs the transaction’s operations in their specified order. If an operation fails, the entire transaction fails and any changes from its earlier operations are rolled back. Its fee and sequence number remain consumed.

### 11. Apply upgrades

Finally, Stellar Core applies any protocol upgrades selected by SCP. An upgrade can change ledger state or header values such as the protocol version, base fee, and operation limit. The lifecycle then begins again.

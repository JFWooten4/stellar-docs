Data is stored on the ledger as ledger entries, akin to key-value stores. Each key is a `LedgerKey` instance. Keys state which object we reference, pointing to `LedgerEntry` values. Thus entry instances contain the data stored at that key.

:::note Internal Design

Each `LedgerKey` contains only the fields needed to identify its entry. Those identifying fields also appear in the full entry. For example, an `OfferKey` [contains](https://github.com/stellar/stellar-xdr/blob/v27.0/Stellar-ledger-entries.x#L603-L608) its `sellerID` and `offerID`, while the corresponding `OfferEntry` [contains](https://github.com/stellar/stellar-xdr/blob/v27.0/Stellar-ledger-entries.x#L326-L349) those fields along with the full record of ledger data: `amount`, `price`, [assets](https://github.com/stellar/stellar-xdr/blob/v27.0/Stellar-ledger-entries.x#L55-L67), and more.

:::

## Entry Types

The descriptions below summarize the linked conceptual documentation. The protocol XDR definitions of [`LedgerKey`](https://github.com/stellar/stellar-xdr/blob/v27.0/Stellar-ledger-entries.x#L588-L651) and [`LedgerEntry`](https://github.com/stellar/stellar-xdr/blob/v27.0/Stellar-ledger-entries.x#L548-L586) are the source of truth for the exact fields and types.

### 1. Account {#account}

An `AccountEntry` stores the on-ledger state of a Stellar `G...` account, including its XLM balance, sequence number, thresholds, signers, flags, liabilities, and sponsorship counters. It also tracks the subentries that determine the account's minimum balance. Learn more in the [Accounts section](../accounts.mdx).

- **Key:** Identified by `AccountID`
- **Entry:** Full account record including balance, sequence number, thresholds, flags, home domain, and list of signers. Tracks [subentries](../accounts.mdx#subentries) that drive the minimum balance requirement.

### 2. Trustline {#trustline}

A `TrustLineEntry` records an account's opt-in to hold a non-native asset. It tracks the asset balance, holding limit, authorization state, and buying and selling liabilities, and is created or updated through [`changeTrustOp`](../../transactions/list-of-operations.mdx#change-trust). Learn more in the [Trustlines section](../accounts.mdx#trustlines).

- **Key:** `(AccountID, asset)`
- **Entry:** Trustline state for a non-native asset. Stores the asset balance, limit, authorization flags, and trading liability counters.

### 3. Offer {#offer}

An `OfferEntry` records an account's order to sell one asset for another at a specified price on the SDEX. An unmatched amount remains on the order book until another order or path payment consumes it, or its owner cancels it. Learn more in the [SDEX order books section](../../liquidity-on-stellar-sdex-liquidity-pools.mdx#order-books).

- **Key:** `(sellerID, offerID)`
- **Entry:** A single offer on the DEX. Contains the selling and buying assets, amount, price, and [passive](../../liquidity-on-stellar-sdex-liquidity-pools.mdx#passive-offer) flags.

### 4. Account Data {#account-data}

A `DataEntry` stores an arbitrary name-value pair attached to a Stellar account. It is created, updated, or removed through [`manageDataOp`](../../transactions/list-of-operations.mdx#manage-data) and is distinct from smart contract data.

- **Key:** `(accountID, dataName)`
- **Entry:** Arbitrary key-value pair (`DataValue`) attached to an account.

### 5. Claimable Balance {#claimable-balance}

A `ClaimableBalanceEntry` holds an asset for one or more potential claimants until a claimant's predicate is satisfied. This allows a sender to create a payment before the recipient is ready to receive it, although a recipient still needs a trustline before claiming a non-native asset. Learn more in the [Claimable Balances guide](../../../../build/guides/transactions/claimable-balances.mdx).

- **Key:** `balanceID`
- **Entry:** Tracks the asset, amount, claimants, [predicates](../../../../build/guides/transactions/claimable-balances.mdx#other-parameters), and optional flags.

### 6. Liquidity Pool {#liquidity-pool}

A `LiquidityPoolEntry` stores the shared state of a constant-product market between two assets, including its parameters, reserves, total pool shares, and trustline count. Deposits and withdrawals update this state, while path payments can use the pool to exchange assets. Learn more in the [Liquidity Pools section](../../liquidity-on-stellar-sdex-liquidity-pools.mdx#liquidity-pools).

- **Key:** `liquidityPoolID`
- **Entry:** Holds pool parameters (two assets, fee rate), reserves, total pool shares, and a pool's trustline count (to prevent entry scanning).

### 7. Contract Data {#contract-data}

A `ContractDataEntry` stores one value under a contract-owned key. Its ledger key combines the owning contract, a contract-chosen value, and the storage durability; host functions let the owning contract read, write, and delete the complete entry. Learn more in the [Persisting Contract Data section](../../contract-development/storage/persisting-data.mdx#ledger-entries).

- **Key:** `(contract, key, durability)`
- **Entry:** Stores the `SCVal` value associated with that key under the contract. Used for Soroban data storage alongside keys.

### 8. Contract Code {#contract-code}

A `ContractCodeEntry` stores uploaded WebAssembly (Wasm) bytecode and its cost inputs, identified by the hash of the Wasm module. Learn more in the [Smart Contracts overview](../../../../build/smart-contracts/overview.mdx).

- **Key:** `hash` of the Wasm module.
- **Entry:** Contains the Wasm bytecode and associated cost inputs to deploy or invoke contracts. [Fee metadata](../../fees-resource-limits-metering.mdx#resource-fee) takes into account component factors like number of instructions, functions, and variables.

### 9. Config Setting {#config-setting}

A `ConfigSettingEntry` stores an active network-level parameter used by smart contract execution, resource limits, fees, or state archival. Validators modify these on-ledger settings through the network-upgrade process. Learn more in the [Soroban Settings section](../../../../validators/admin-guide/soroban-settings.mdx).

- **Key:** `configSettingID` (index of setting [in list](https://github.com/stellar/stellar-xdr/blob/v27.0/Stellar-contract-config-setting.x#L373-L396))
- **Entry:** Active value of a network-level parameter (e.g., protocol limits, compute fees, state archival). The whole validator quorum set has to agree on these values.

### 10. TTL {#ttl}

A `TTLEntry` records the ledger sequence through which an associated contract data or code entry remains live. When that time-to-live expires, temporary data is deleted, while persistent or instance data is archived until restored. Learn more in the [State archival section](../../contract-development/storage/state-archival.mdx).

- **Key:** `keyHash` (hash of associated LedgerKey).
- **Entry:** Defines the expiration ledger sequence (`liveUntilLedgerSeq`) for temporary objects such as contract data or code.

## Working with ledger entries

Most products only need to reason about a subset of ledger entries—for example, accounts, trustlines, and liquidity pools cover the majority of asset and trading use cases. Once you understand how to build and parse a few representative keys and entries, you can extrapolate the same patterns to the remaining entry types.

Ledger entries are always mutated through transactions: operations either create, update, or delete these records as part of applying a transaction set. Use [`getLedgerEntries`](../../../../data/apis/rpc/api-reference/methods/getLedgerEntries.mdx) when you need to fetch the raw on-ledger representation for debugging or cross-checking derived data.
